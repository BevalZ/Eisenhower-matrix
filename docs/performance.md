# 性能机制与回归检查

优化分两轮：**第 9 轮**（基线 `b373c96`，2026-10-25）处理刷新、批处理、拖拽几何与包体积；**第 10 轮**（基线 `4a135a3`，2026-10-29）把「整表刷新」和「全部卡片挂载」这两条主路径换成增量刷新与虚拟列表。两轮都保持 SQLite 持久化、同步冲突规则、任务排序和撤销语义。数据均为生成的测试任务，不读取真实任务库。

## 已落实的机制

| 路径 | 机制 | 约束 |
| --- | --- | --- |
| 任务刷新（增量） | 前端带上次的 `(generation, watermark)` 调 `get_tasks_delta`，只取水位之后写入的行与已删除 id | 首次加载、批量命令后（导入/WebDAV 恢复/多端同步）取全量；每 20 次增量强制一次全量兜底 |
| 任务刷新（合并） | 同一时刻最多一个读取；同步事件合并；读取期间再次失效只补一次最新读取 | 拖拽和写入期间暂停应用快照，过期结果丢弃；失败后可以重试 |
| 任务状态 | 按 ID 复用对象；无变化且顺序相同时复用数组；增量结果为空时连数组都不换 | 避免无变化刷新重新排序、分组和更新所有卡片 |
| 看板渲染 | 每象限一个 `QuadrantColumn`，超过 200 行才开窗口：只挂载视口附近的行，上下用占位块补高度 | 200 行以内完全走原来的全量渲染，落点仍由真实 DOM 几何决定 |
| 行高 | 已挂载卡片实测高度 + 未挂载行按「有/无描述」的滚动均值估算 | 没在屏幕上出现过的行，滚动条长度是估算值；窗口尺寸变化会清空实测缓存 |
| 拖拽 | 全量模式用 DOM 二分落点；窗口模式用前缀偏移二分（含占位高度补偿） | DOM 更新后清缓存；每帧读取 O(log n) 个位置，不缓存会变化的坐标 |
| 拖拽重渲染 | 拖拽期间只有指针所在列会重渲染（其余列 props 未变），行数组只在拖拽开始/结束时重建 | 跨象限移动仍然按原样重新挂载卡片 |
| 键盘移动 | 移动到窗口外的行时先滚动到该行再聚焦（`ensureVisible`） | 只在窗口模式下需要；全量模式是空操作 |
| 看板布局 | 网格行使用 `minmax(0, 1fr)`，设置 `min-height: 0` | 大列表在象限内滚动，避免整个网格被内容撑高 |
| 提醒时钟 | 只对「有截止时间」的任务构建签名，签名变化才重新检查 | 去重缓存仍按当前任务清理，首次加载前不清缓存 |
| 初始加载 | 设置、统计、向导、编辑按需加载；悬浮球独立入口 | 悬浮球不实例化任务状态、不订阅任务同步、不拉取任务列表 |
| 生命周期 | 异步事件注册归属组件作用域；晚到的注册也会释放 | 关闭组件后忽略回调；隐藏主窗口延后远端刷新并暂停提醒定时器 |
| 本地写入时间戳 | 每次写入取「墙钟或上一个戳 +1」中较大者（`last_stamp`），保证严格递增 | 导入/合并后重新对齐表内最大时间戳，跨设备冲突仍按 `(updated_at, updated_by)` 决胜 |
| SQLite | 导入、排序、恢复复用预编译语句；同步缓存语句且只读冲突判断元数据；读取用 `prepare_cached` | 保留事务原子性、时间戳与设备 ID 决胜、旧协议保留本地截止时间 |
| 数据库锁 | 同步每 2000 条释放一次互斥锁；JSON 导出序列化在锁外 | 让前台命令有机会获得锁，不保证线程调度公平性 |
| UI 线程 | 任务 CRUD、统计、设置读取、导入导出使用 `spawn_blocking` | SQLite 与系统凭据读取不会占用窗口线程 |
| 查询 | 活跃任务部分索引匹配 `done ASC, priority DESC, id ASC`；增量查询按 `updated_at` 过滤可见行与墓碑 | 看板查询无需临时排序；删除墓碑不进入索引 |

### 增量刷新协议

`get_tasks_delta(generation, watermark)` 返回 `{ generation, watermark, full, tasks, removed }`：

- `watermark` 是表内（含墓碑）最大的 `updated_at`，前端回传它换下一次增量；本地写入的戳严格递增，所以「大于水位」的查询不会漏行（同一毫秒内的连续写入也能各自拿到不同的戳）。
- 导入备份、WebDAV 覆盖恢复、多端合并会重写整表或带入对端较旧/较新的时间戳，这些路径把 `generation` +1，拿着旧游标的前端会收到 `full: true` 的全量快照。
- 前端另有两条兜底：应用启动、以及每 20 次增量之后强制一次全量；导入/同步/清除已完成等批量命令后立即丢弃游标。

## 测量结果

Windows、Node 26.1.0、Vue 3、Vite 5.4.21；浏览器为 Edge；窗口 1100 × 750。耗时是单机合成基准，不代表所有设备；硬性检查使用操作数量、对象身份与资源预算。

### 第 10 轮（1 万任务，对比第 9 轮构建）

| 场景 | 基线 `4a135a3` | 本轮 |
| --- | ---: | ---: |
| 首屏出现第一张卡片（含夹具生成 1 万条） | 16.8 s / 17.1 s | 3.2 s / 3.3 s（预热后一次 0.6 s） |
| 已挂载卡片 | 10,000 | 36 |
| `.board` 内 DOM 元素 | 163,380 | 638 |
| 虚拟列表总高度（滚动条） | 217,508 px | 217,516 px |
| 拖拽 12 次落点变化的 DOM 变更 | 79 次（6.6 / 次） | 55 次（4.6 / 次） |
| 滚动 20 步（每步 5% 列表高度） | 133–146 ms / 步，0 次变更 | 23–26 ms / 步，≈ 34 次变更 / 步 |
| 1000 任务下 100 次同步事件的 DOM 变更 | 0（1 次整表读取） | 0（1 次增量读取，载荷为空） |
| 主窗口初始 JS，含所有静态依赖 | 134,050 B | 138,985 B（预算 143,360 B） |

悬浮球入口没有改动（101,776 B → 101,784 B），但重跑悬浮球对比仍可验证它不受影响：两个构建里悬浮球的任务读取都是 0，1 万任务夹具下强制 GC 后的 JS 堆分别是 3,550,368 B 与 2,972,264 B —— 绝对值在两次运行之间本就有波动，不要把差值当成收益。

窗口模式要付的代价是滚动时挂载/卸载卡片：每滚动 5% 的列表高度约产生 34 次 DOM 变更（对应 6–7 张卡片的进出），换来的是每步 5 倍的时间下降和 250 倍的元素数量下降。200 行以内的象限不开窗口，行为与第 9 轮完全一致。

### 前端合成基准（`npm run perf`，数字仅作记录）

- 1 万任务、10 次无变化刷新：0 次重新排序，数组与对象身份不变。
- 1 万任务、50 次空增量 + 1 次单行合并：累计 0.15 ms，只有 1 个对象被改写，其余 9,999 张卡片身份不变。
- 5000 项批量排序：约 13 ms，5000 次 ID 读取（原逐条扫描 12,502,500 次）。
- 落点几何读取：1 万卡片最多 14 次二分读取。

## 可复跑的检查

```sh
npm test          # 含操作数量、对象身份与资源生命周期回归
npm run perf      # 单独输出合成基准
npm run perf:bundle
cd src-tauri
cargo test        # 本机缺 MSVC 链接器，实际由 CI 执行
```

`npm test` 已包含操作数量与资源生命周期回归；`npm run perf` 单独输出合成基准。包体积检查遍历 Vite manifest 的静态依赖，主窗口预算为 JS 140 KiB / CSS 24 KiB，悬浮球为 JS 110 KiB / CSS 10 KiB；超过预算会失败。CI 在前端构建后自动运行此检查。不要仅为了让 CI 通过就抬高预算。

测试扫描限定 `src`，避免 `output/` 中的历史源码副本被重复计入。临时基线保留在已忽略的 `output/performance/`（自动审批阻止了递归清理），不影响构建与测试。

浏览器验证使用 Tauri IPC 夹具，覆盖 1000 条任务、事件风暴、统计页往返、设置/向导按需加载、跨象限拖拽、键盘移动及编辑；第 10 轮追加了窗口模式的四项检查（挂载数量、滚到底部、深处卡片拖出、远端增量改动）与一个小列表对照检查：


## 验证范围与后续

- 前端：110 项测试通过，类型检查、生产构建、包体积预算通过。
- Edge 生产构建（1000 任务）：100 次同步事件只读取一次、稳定看板 DOM 变更为 0；统计页往返 4 次后监听恢复到 1；拖拽、键盘移动（含窗口列滚动定位）、编辑、弹窗通过；窗口模式挂载 36 张卡片、滚到底部能看到第 1000 张、深处卡片可拖出；远端单行改动经增量读取就地更新。小列表（120 任务）全部挂载、无占位块、拖拽照旧。
- Rust：本机 `cargo test --ignore-rust-version` 因缺少 MSVC `link.exe` 无法链接（PATH 上的 `link.exe` 是 Git 自带的 coreutils），`cargo check --all-targets` 通过，完整测试由 CI（ubuntu）执行。第 10 轮新增 4 个增量协议用例：首次全量、只带变更行与删除 id、批量重写后回落全量、对端时钟超前时的合并与本地写入。
- 本机未测 Android 真机、原生 WebView2 总内存和真实磁盘写入延迟；未修改持久化耐久性设置。
- 仍未实现：同步传输仍是全量快照（分页/增量协议属于后续工作）；未挂载行的高度是估算值，窗口尺寸剧变后在滚动到该行之前滚动条长度会有偏差。
